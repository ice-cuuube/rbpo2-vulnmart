# Экспертная оценка безопасности

## 1. Общая информация
Объектом исследования является учебный программный комплекс VulnMart-Lab, разработанный специально для практической работы №2.
Комплекс содержит три программные части: Python-приложение на Flask, C++-программу и JavaScript-приложение на Node.js и Express.
Уязвимости были встроены намеренно для демонстрации методов SAST и DAST.
## 2. Python
### SQL Injection
В Python-приложении пользовательское значение username включается непосредственно в строку SQL-запроса.
Проблема классифицируется как CWE-89.
Основная причина заключается в формировании SQL-команды через конкатенацию значения, полученного от пользователя.
Рекомендация: использовать параметризованные SQL-запросы.
### Stored XSS
Пользовательский отзыв сохраняется, а затем выводится с отключением HTML-экранирования.
Проблема классифицируется как CWE-79.
Рекомендация: применять контекстное экранирование пользовательского вывода и избегать отключения автоматического escaping.
### Incorrect Authorization / IDOR
Доступ к заказу выполняется по идентификатору без проверки принадлежности объекта текущему пользователю.
Проблема классифицируется как CWE-863.
Рекомендация: перед выдачей объекта проверять права текущего пользователя.
### Hard-coded Credentials
Пароль административной панели хранится непосредственно в исходном коде.
Проблема классифицируется как CWE-798.
Рекомендация: хранить секреты во внешнем защищённом хранилище и не включать пароли в исходный код.
## 3. C++
### Buffer Overflow
В программе используется strcpy для копирования пользовательского ввода в буфер фиксированного размера.
Проблема классифицируется как CWE-120.
Рекомендация: ограничивать длину входных данных и использовать безопасные операции работы со строками.
### Format String
Пользовательская строка передаётся непосредственно функции printf как строка формата.
Проблема классифицируется как CWE-134.
Рекомендация: использовать фиксированную строку формата, а пользовательские данные передавать отдельным аргументом.
### OS Command Injection
Пользовательский ввод включается в строку системной команды, после чего используется функцией system.
Проблема классифицируется как CWE-78.
Рекомендация: не передавать непроверенные данные в shell-команды и использовать безопасные механизмы запуска процессов.
## 4. JavaScript
### SQL Injection
В JavaScript-приложении параметр username напрямую включается в SQL-запрос.
Проблема классифицируется как CWE-89.
Использование sql.js изменяет механизм реализации SQLite, но не устраняет саму логическую ошибку формирования SQL-запроса.
Рекомендация: применять параметризованные запросы.
### XSS
Параметр name непосредственно включается в HTML-ответ.
Проблема классифицируется как CWE-79.
Рекомендация: выполнять безопасное экранирование данных перед их включением в HTML.
### OS Command Injection
Параметр host передаётся в child_process.exec через динамически сформированную команду.
Проблема классифицируется как CWE-78.
ESLint с security-плагином обнаруживает данную конструкцию как потенциально опасное использование exec.
Рекомендация: использовать безопасный запуск программы с передачей аргументов отдельно, например execFile или spawn, а также ограничивать допустимые значения.
## 5. SAST
Статический анализ проводился средствами Bandit, Cppcheck и ESLint.
Результаты инструментов были сохранены в исходных форматах.
Следует учитывать, что SAST не гарантирует обнаружение всех классов ошибок. Особенно это относится к ошибкам бизнес-логики и контроля доступа.
## 6. DAST
Динамический анализ проводился средствами OWASP ZAP и дополнительными ручными HTTP-проверками.
ZAP Baseline использовался для пассивного анализа запущенных HTTP-сервисов.
Ручные проверки применялись для исследования поведения приложения при передаче пользовательских значений и доступа к объектам по идентификаторам.
## 7. Связь CWE и CVE
CWE использовался для классификации типа слабости.
CVE использовался только как пример реально опубликованной уязвимости соответствующего класса.
Наличие CVE в датасете не означает, что учебный проект VulnMart-Lab имеет этот CVE.
CVSS, указанный в датасете, относится к соответствующей реальной CVE, а не является самостоятельно рассчитанной оценкой учебного кода.
## 8. Общие рекомендации
1. Использовать параметризованные SQL-запросы.
2. Экранировать пользовательский вывод.
3. Проверять права доступа перед возвратом объектов.
4. Не хранить пароли в исходном коде.
5. Ограничивать размеры буферов в C++.
6. Не использовать внешний ввод как строку формата.
7. Избегать shell-интерпретации пользовательского ввода.
8. Регулярно проводить SAST и DAST.
9. Проверять зависимости проектов.
10. Использовать автоматизированные проверки безопасности при разработке.
## 9. Итог
Исследование показало, что один инструмент анализа не может обнаружить все типы слабостей.
SAST позволяет находить потенциально опасные конструкции в исходном коде, DAST показывает поведение работающего приложения, а ручной анализ необходим для проверки логики доступа и других ошибок, зависящих от контекста.
Полученный комплекс результатов был объединён в структурированный датасет и дополнен экспертной оценкой.
